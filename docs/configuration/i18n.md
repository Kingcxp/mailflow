# i18n

## Built-in packs

- `en` (English) — the complete baseline; every key is defined here.
- `zh-CN` (简体中文) — Simplified Chinese; key parity with `en` is enforced
  by a unit test.

The default language is `en`. Switch with `lang set <code>` in the command
shell or the Settings tab of the TUI; the choice is persisted by the storage
backend (`preferences.language`) and restored on the next start.

## External packs

Other languages load as **data-only JSON** files from configured
directories (`[i18n] extra_dirs`):

```json
{
  "locale": "ja",
  "name": "日本語",
  "messages": {
    "mail": { "list_title": "メール（{count}）" },
    "command": { "help": { "title": "MailFlow コマンド" } }
  }
}
```

- `locale` — the code users select; `name` — the display name; `messages` —
  a nested object of keys. Nested keys are flattened with dots.
- A **partial** pack is fine: any missing key falls back to English, then to
  the key itself.
- Packs are executable-code-free: no Python, only data.

See `translations/example.ja.json` for a sample (loaded from the
`translations/` directory in the example configs).

## Key conventions

- Dotted namespaces: `command.help.title`, `mail.list_title`,
  `tui.reply_prepared`, `config.desc.general.workers`, `cli.shell_prompt`, ...
- `{name}` placeholders are formatted with `str.format` parameters
  (`service.t("mail.not_found", mail_id="m1")`).
- **`t()` only formats when parameters are passed.** A message with no
  parameters is returned verbatim, so text containing literal braces — e.g. a
  `${ENV_VAR}` example inside an option description — needs no escaping. A
  message that *does* take parameters must escape any literal brace as
  `{{ }}`, because it goes through `str.format`.
- A formatting failure is logged and the unformatted message is returned; it
  never raises into the caller.
- All user-visible strings in Core commands, the CLI, the TUI and notifiers
  go through `service.t(...)` / `I18n.t(...)`.
- The English pack must contain English text. A translated string left in
  `en.json` is a bug (invariant 31), because English is also the fallback for
  every partial external pack.

## Namespaces in the built-in packs

458 keys per pack at the time of writing:

| Namespace | Covers |
| --------- | ------ |
| `common`, `command` | shared words, command parsing/help |
| `mail`, `action`, `trash`, `reply` | the mail, action, trash and reply commands |
| `plugin`, `adapter`, `account`, `llm`, `runtime`, `update` | inspection and lifecycle commands |
| `config` | `config` command output plus `config.desc.<dotted.key>` — one localized description per configurable option (70 of them) |
| `tui` | every TUI label, tab title, button, hint and status message |
| `cli`, `feedback`, `lang` | CLI host strings, feedback command, language switch |

`config.desc.*` entries are generated for both packs by
`tools/gen_option_descriptions.py`, which refuses to write when the English
and Chinese key sets differ. Add a new option's description there, not by
hand-editing the JSON.
